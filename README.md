# Julia — сайт психолога с защищёнными заявками

> Экспериментальная реализация, **не готова для сбора настоящих чувствительных данных** до эксплуатационной и правовой проверки.

## Состав

- `frontend/index.html` — существующий публичный сайт (дизайн и страницы сохранены); 3 формы отправляют данные в API.
- `frontend/admin.html`, `frontend/admin.js`, `frontend/admin.css` — кабинет Юлии по `/admin`.
- `backend/app/main.py` — FastAPI, валидация форм, шифрование контактных данных, PostgreSQL, Telegram.
- `backend/app/admin.py` — вход по паролю и TOTP 2FA, сессии в БД, изменения статусов, удаление заявок, журнал действий.
- `tests/test_app.py` — тесты обработки заявок и входа.

**Важно:** это заявки на запись, а не бронирование конкретной даты или автоматическое подтверждение сеанса. Слоты и календарь пока отсутствуют.

## Что происходит при записи

1. Клиент заполняет имя, контакт, необязательный запрос и даёт явное согласие на обработку персональных данных.
2. Сервер проверяет ввод, шифрует имя, контакт и текст обращения ключом Fernet, сохраняет в PostgreSQL.
3. Telegram-бот отправляет Юлии **только номер заявки** (без имени, телефона, тематики и текста).
4. Юлия заходит по HTTPS в `/admin`, вводит пароль и одноразовый код, читает заявку и меняет статус: новая / связались / подтверждена / отменена.
5. Уведомление не удалось отправить? Заявка остаётся в базе со статусом `pending`. Повтор отправки происходит при новых заявках, вручную из админки **или через отдельно настроенный cron-воркер** (см. ниже). Если отдельный cron не включен, уведомления могут задерживаться.

## Railway: настройка тестового окружения

1. Создайте в Railway отдельное тестовое окружение или сервис из GitHub-ветки `feature/secure-booking-backend`. **Не переключайте production до успешной проверки.**
2. Добавьте плагин PostgreSQL и передайте `DATABASE_URL` сервису через внутреннюю Railway variable reference (не вставляйте пароль БД в репозиторий).
3. Создайте переменные в Railway сервисе (образец в `.env.example`):
   - `FIELD_ENCRYPTION_KEY` — ключ Fernet. Сгенерировать в безопасной локальной среде: `python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"`
   - `RATE_LIMIT_SECRET` — длинный независимый случайный секрет: `python -c "import secrets; print(secrets.token_urlsafe(48))"`
   - `ADMIN_PASSWORD_HASH` — **только Argon2id-хеш** длинного уникального пароля (не сам пароль): `python -c "from argon2 import PasswordHasher; import getpass; print(PasswordHasher().hash(getpass.getpass()))"`
   - `ADMIN_TOTP_SECRET` — отдельный TOTP secret для приложения-аутентификатора: `python -c "import pyotp; print(pyotp.random_base32())"`. Вручную добавьте ключ в приложение TOTP Юлии; используйте защищённый канал для настройки.
   - `TELEGRAM_BOT_TOKEN` — токен нового бота из [@BotFather](https://t.me/BotFather).
   - `TELEGRAM_CHAT_ID` — идентификатор **личного** чата Юлии с ботом (бот не может написать ей раньше, чем она начнёт диалог, например `/start`). Получить ID можно локально запросом метода `getUpdates` Bot API после `/start`, не разглашая токен и историю сообщений. Убедитесь, что он относится к нужному чату.
   - `PUBLIC_ORIGIN` — необязательный точный URL сайта (например, `https://example.com`) для same-origin проверки; по умолчанию используется Host запроса.
4. В Railway запускается `Dockerfile`. После развёртывания используйте `https://<тестовый-домен>/api/health` и `https://<тестовый-домен>/admin`. Убедитесь в HTTPS.
5. Проверьте тестовую заявку: пришло сообщение только с номером, данные появились в кабинете, можно менять статус и удалять. Проверьте отсутствие Telegram токена и персональных данных в логах и письмах. Проверьте восстановление базы и ключа из резервной копии.

### Повтор уведомлений по расписанию

Для более надёжной доставки создайте в Railway **отдельный Cron-сервис** из той же ветки. Используйте тот же PostgreSQL и переменные `DATABASE_URL`, `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`. В Railway настройте **Start Command** `python -m backend.app.worker` и расписание `*/5 * * * *` (раз в 5 минут). Для cron-сервиса не нужен публичный домен. Основной сервис сайта по-прежнему запускает uvicorn через Dockerfile; не заменяйте его Start Command командой воркера.

Cron-воркер отправляет до 50 ожидающих уведомлений за запуск. Возможны дубли при сбое после отправки, но до фиксации статуса в БД. Проверяйте журнал задач и статусы pending в админке. Расписание должно быть настроено отдельно: сам факт наличия файла worker **не включает автоматический запуск**.

**Никогда** не передавайте пароли, токены, TOTP-секреты или данные клиентов в чат или GitHub. Ключ Fernet храните отдельно и защищённо: его потеря означает невозможность расшифровки существующих обращений. При утечке ключа требуется отдельный план ротации и пере-шифрования.

## Безопасность и ограничения

- Пароли администратора: Argon2id. Второй фактор: TOTP. Сессия — случайный непрозрачный токен в `Secure; HttpOnly; SameSite=Strict` cookie, токен хранится только в виде SHA-256 в БД, время жизни — 8 ч.
- Запросы изменения/удаления защищены CSRF-токеном и проверкой Origin. Просмотр и изменение фиксируются журналом без открытых клиентских данных.
- Поля клиентских заявок шифруются на уровне приложения, на страницах админки пользовательские значения добавляются через `textContent`, а не `innerHTML`.
- Базовое ограничение количества заявок — 5 на один HMAC-хеш контакта / 15 минут. Лимиты входа — 5 попыток на IP-хеш и 30 глобально / 15 минут. Это **не** комплексная защита от массового спама, DDoS, утечки, фишинга и XSS.
- Отправка уведомлений — best effort, с ручным повтором. Возможны дубли при обрыве соединения после успешной отправки. Нужен отдельный воркер/очередь, мониторинг зависших `pending` и аварийные оповещения.
- **Нет** автоматического срока хранения, безопасной процедуры восстановления, MFA с защитой от повторного использования TOTP, полноценной миграции схемы БД (Alembic), ротации ключей, внешнего аудита. Добавление новой таблицы реализовано через `create_all`, которое **не мигрирует существующие столбцы**. Перед production обеспечить миграции и тест резервного восстановления.
- Пользовательский HTML унаследован без полного аудита сторонних ссылок и скриптов. Публичная страница и админка пока работают на одном домене. Разделение доменов, строгая CSP публичного сайта, защита от XSS, серверные ограничения размера запросов и безопасная настройка reverse proxy — задачи перед production.
- Политика конфиденциальности в исходном HTML должна быть проверена и адаптирована под фактическую обработку заявок, получателей, хранение, удаление, страну хранения БД и применимое законодательство. Данные о психологических запросах могут относиться к особым категориям данных. Для российских клиентов отдельно проверьте требования 152-ФЗ, локализацию и передачу данных за рубеж. Сам код **не гарантирует юридическую или медицинскую конфиденциальность**.
- Клиентские пароли и учётные записи **не собираются**, потому что их нет в текущем продукте. Нельзя хранить пароли клиентов в открытом виде; если клиентские аккаунты будут добавлены, потребуется отдельная схема аутентификации и сброса.

## Проверка

GitHub Actions устанавливает зависимости, запускает `pytest`, проверяет синтаксис Python, встроенного JavaScript и собирает Docker-образ.

Не добавляйте реальных клиентов и не публикуйте боевой домен до прохождения интеграционных проверок в Railway и правовой оценки.
